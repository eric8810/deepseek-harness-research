# 《A Programming Paradigm for Spatiotemporal Composability》读后感

## 一、背景需求:从"插件重启"到"自我演化的 agent harness"

这篇论文想解决的工程痛点其实非常具体,而且论文自己也给出了量化的证据。作者以 VSCode 为靶子:扩展宿主把成百上千个扩展跑在同一个进程里,却没有任何机制在运行时卸载某一个扩展的代码——一旦 `activate` 跑完,禁用或卸载就只能重启整个宿主;在安装量前 100 的扩展里,87 个带可执行代码、全部受此约束。空间维度上更惨:`extensionDependencies` 在前 100 名里只有 7 个在非内置扩展间声明了依赖,而跨扩展交互的 `getExtension().exports` 类型是 `any`,根本没有结构契约(§1.2.1)。这两条分别对应论文定义的"时间可组合性"(卸载时副作用被完整反转)与"空间可组合性"(依赖可声明、可发现、可反应式解析)。

真正让这个问题"到了该解决的时候"的,是论文反复提到的 self-evolving agent harness(§1.2.2):未来的 agent harness 要在持续服务请求的同时,生成并部署对自己的组件的修改。这里的关键不是"方便",而是**生存**——没有时间可组合性,每一次自我修改都要重启、丢掉进程内所有累计状态;更糟的是,一个错误的自我修改可能直接把用于恢复的那个进程本身弄瘫痪。这正是当前 DeepSeek 这种基础设施厂商的处境:harness 不再是人写的静态程序,而是 agent 持续改写自己的运行时。本文所在的仓库 `deepseek-harness` 本身就是把 Cordis 整体 vendoring 进来、让"agent 修改自身运行时"成为一等公民的产品,AGENTS.md 里就有 `demo:cordis` 这种让 agent 改自己运行时的演示。所以这不是一篇"先有理论再找应用"的论文,而是"生产框架缺理论基础"被补上的一篇。

论文还批判了粗粒度替代品(§1.2.3):操作系统在进程粒度给时间可组合性,容器编排在服务粒度给空间可组合性。粒度错配的代价是重启丢状态、冗余副本,以及把本地的函数调用网络化。这个批评站得住,但要注意它的立场:它预设"更细粒度永远更好",而实际工程里进程/容器边界带来的**失败隔离**恰恰是它想用范式来替代的东西——这一点论文在 §6.3 才勉强承认(沙箱是语言层之外的事)。这是后面要批判的地方。

## 二、领域认知:谱系如何被整合,又付出了什么代价

这篇论文最漂亮的地方,是把两个原本是"静态类型注解"的东西**物化为运行时机制**。古典 effect system(Lucassen–Gifford 的类型化副作用、Moggi 的 monad、Plotkin–Power 的代数效应与 handler)与 coeffect system(Petricek 的 comonad、Orchard 的 graded modal types)都只在词法固定作用域内、编译期做分析;而动态组合要求的是"运行时到达和离开的组件、持续演化的上下文"。作者没有选择把类型系统做得更厚,而是反其道:把 effect 和 coeffect 的概念结构**reify 成运行时可以直接操作的一等实体**(§2.3 末尾那段是全文的方法论宣言)。

具体地,形式化部分有几个实质贡献:

**可逆效应(twisted composition monoid 与 effect 塔)**。把每个 context 变换配对显式逆元,`track`/`recover` 配上累加器 φ(γ)=γ₀ 的不变式(§3.1.1),让"恢复"成为结构保证而不是书写约定。Definition 8 的"按状态取逆"和 Definition 9 的 ◇ 合成是真正的想法:一个原子效应可以针对它实际应用的状态选择逆,复合逆由原子逆的合成自动导出——这直接兑现了"组件卸载路径由加载路径派生,而不是另外手写"(§3.3.3)。effect iterator(Definition 51)把激活建模成可中断的迭代器,并指出它就是 reified delimited continuation、映射到主流语言的 `yield`——这个工程直觉非常值钱,它让形式化能直接落到生成器上。

**响应式 coeffect 与顺序约束**。satisfaction predicate(§3.2.2)可判定、通知把每次 context 变迁分类为 activating/deactivating/neutral,这让"组件只在依赖齐备时激活"成为结构性质。但真正的精华在 §4.3.1 的 withdrawal 层:单纯的通知无法保证"消费者卸载时仍能读到正在被撤走的依赖"(连接池要先把连接还回去),所以作者拆出 L-Leave(立即停止对外提供,但保留自身 committed view)与带 guard 的 L-Unload,Theorem 63 证明"提供者只有等所有消费它的 fiber 都走完才撤走绑定"。这是全文最细腻、最接近真实工程痛点的定理,也是实现里 `unload` 的 Line 25"先 drain 依赖者再跑 dispose"的直接依据。

**元理论的质量**。十规则演算(§4.3)配上 preservation、recovery exactness、ordering、resolution coherence、progress(带 S(n) ≤ (K+4)(V(n)+1) 的终止上界)、confluence 六个定理,并且**真的给了证明**而不是素描——这在"应用系统论文"里是不常见的扎实程度。confluence(Theorem 73)承诺动态历史不留痕迹:系统最终 quiesce 到的状态,等于从头按依赖序静态装载一遍的结果,这直接为声明式 loader 的"增量 reconciliation 是安全的"提供了依据(§5.2.1)。

**代价也如实列出来了,而且不小**:

1. **逆元的正确性是"义务"而非"性质"**。§5.1.1 自己承认:`ctx.effect` 不检查 witness——回调提供逆元,逆元是否真的恢复它伴随的效应,"是组件作者的义务,而不是运行时验证的性质"。也就是说,整座形式化大厦证明的是"在 witness 成立的前提下,恢复是结构保证",而 witness 本身是未验证的程序员代码。这比 VSCode 的 deactivate 好(复合逆由原子逆合成、LIFO 顺序自动),但"结构性保证"这四个字被大大稀释了——它仍是"原子逆元正确"这一信任链上的推论。
2. **独立性/可交换性是强假设**。Theorem 61 和 73 都要 pairwise independence,Theorem 42 要求所有 key 可交换。但中件链(ordered chain)这类效应天然不可交换(§3.3.2 自己举了例子),此时要么靠组件内累加器 LIFO、要么靠跨组件的声明顺序。Corollary 21 的"任意顺序恢复"只有在独立性成立时才有;现实里大量注册型效应确实可交换,但一旦遇到顺序敏感的,系统的承诺就缩回"LIFO 或声明序"。
3. **观测等价击穿了"完全恢复"**。§3.3.2 开篇就承认物理状态无法还原:`free` 不会把堆布局还原成 `malloc` 之前的样子。于是定理里的 "=" 全部要读成 "≃",而 ≃ 由"绑定在 key 上的操作能观察到什么"决定——**没有绑定到任何 coeffect key 的位置被直接遗忘**。换句话说,时间可组合性的真正承诺是"恢复所有可见于已声明 coeffect 接口的东西",而不是抽象层面承诺的"完整反转"。论文诚实,但诚实暴露了卖点与承诺之间的落差。
4. **统一 context 的"统一"有化妆成分**。Γ∞ = μΓ.Γ×(Γ→Γ)×Σ(Definition 32)本质是把 effect 上下文(带累加器的塔)和 coeffect 上下文(依赖表)放进一个**乘积**里再递归。说它"统一"了两种上下文,不如说是"让一切交互都经过同一个 ctx"这个设计声明。§3.3.3 把它与 State monad 的显式穿线、命令式的隐式突变(React `useEffect`、Spring `getBean`)并列为三种范式,这个定位叙事很强,但"context 即范式"更像修辞而非新的数学结构。

## 三、作者目的:Cordis 的理论包装与 DeepSeek 的战略意图

作者是北京大学(Yifan Shi、Wei Zhang)+ DeepSeek-AI(Yifan Shi、Tianyi Cui)。论文的形式化对象正是开源框架 Cordis——而 Cordis 正是当前工作仓库 vendoring 进来、被改造成 `@deepseek-ai/cordis` v4.0.0-rc.7 的那套"一切皆插件"的运行时。脚注 4 明说"Koishi 目前用 Cordis v3,本文介绍 v4"。所以这篇论文的真实身份是:**为 DeepSeek 基础设施层中实际在用的框架写一本"理论说明书"**,并把它升格为"范式"。

我看作者的战略意图有三层:

1. **为开源框架补学术合法性**。Cordis 的出身是聊天机器人框架 Koishi(4000+ 社区插件,§5.3),圈层是二次元 bot。把这样一个"玩具生态"的形式化抬到"programming paradigm"的高度,是在为它争取编程语言/软件工程主流社区的话语权——这是"作者真正想达成的目的"里最直接的。
2. **为自我演化 agent harness 备理论弹药**。论文把"self-evolving agent harnesses"放在引言动机和结论展望的两端(§1.2.2、§8),并明确说"在无人工监督下、由 AI 生成并替换自己的 harness 组件"是未来验证方向。结合 DeepSeek 的身份,这篇论文的战略重心不是插件系统,而是**让 agent 运行时能被 agent 自己安全地持续改写**——时间可组合性保证改坏能回滚、空间可组合性保证依赖拓扑变动时不炸——这正是 harness 产品(GitHub/Anthropic 的 harness engineering、本仓库的 deepseek-harness)都在争的制高点。论文等于提前为这个赛道画了"形式化地基"的旗帜。
3. **范式营销与语言无关的野心**。§6.4、§6.7 论证"context paradigm 语言无关、可与语言和操作系统共同设计",把范围从 TS/Node 扩展到 WebAssembly、native `dlopen`、乃至"以 coeffect 方式提供内存和 fd 的操作系统"。这是在给一个库的抽象争夺"未来系统的公共原语"地位。

## 四、批判性评估:强在哪里、弱在哪里、鸿沟在哪里

**最强的三点**:一是元理论完整且有证明,confluence/progress/ordering 相互咬合,证明里还能看到对"guard 为什么不死锁"的细致论证(Unloading 后 fiber 的表离开 σγ,消费它的 target 随之失效);二是 §4.3 逐步撤掉 atomic/immediate/infallible 三个理想化假设、一路推到十规则真实演算的写作结构,让抽象与实现之间有了可追踪的桥梁;三是对真实约束的诚实(系统边界、emission 不可回滚、补偿、观测等价),这比多数"全知全能框架"论文可信得多。

**最弱的三个点**:

1. **形式化与实现的鸿沟,由本仓库的 vendoring 日志直接暴露**。形式上十个规则、全函数、无调度、无重入;实现里是 TS 的 async/Proxy、并发通知、重入性销毁。vendor/README.md 的"Local modifications"里列了十几条生命周期加固——重入的 dispose 缺口、UNLOADING 期间禁止创建 effect、并发 apply 交错的死锁、HMR 初始扫描与 Include 初装的竞态、Windows 下 rename 的 EACCES 重试……这些**模型根本看不见、也解释不了的现实**,全都得靠手工补丁压下去。论文说"算法忠实于定理"(Table 2 的 correspondence),但在"并发交错、重入、失败顺序"这些真实运行时才有的事上,理论与实现的对应是叙事性的,不是被证明的。
2. **confined / total-on-provision 是未强制的义务**。Definition 48(confined to n)和 Definition 69(total on its provision)是几个关键定理的假设,但实现没有任何机制验证一个组件的 effect 是否"只写自己的表、只读自己声明的 key"。一个通过闭包或全局变量摸到别的 fiber 上下文的组件(§6.7 警告的情形),破坏恢复却不被检测——这正是我最想验证/质疑的一点:这套范式在"独立第三方插件"生态里,安全性靠的是每个作者都写对逆元、都不越界,而这恰好是论文一开始用来批评 VSCode 的"developer discipline"。从"纪律"到"结构保证"的转化,只完成了一半(复合部分),原子部分仍是纪律。
3. **案例是存在性证明,不是量化对比**。§5.3 的 threats to validity 自己承认:单一生态、单一语言、观测性而非对照实验。4000 插件只能证明"这套东西能跑起来",证明不了"它比粗粒度重启/容器编排省了多少成本"——而 §1.2.3 的成本论证恰恰是论文最重要的动机。

**什么场景下失效或过重**:依赖稀疏、生命周期静态的普通服务(比如一个只有三四个模块、从不热更新的后端),引入完整 fiber/效应/通知机制纯属杀鸡用牛刀;顺序敏感、副作用强烈依赖共享可变外部状态(数据库写入、第三方 API)的组件,emission 部分(§6.1)根本不回滚,范式只能提供"补偿"这种和手写 cleanup 没有本质区别的东西;组件间互依赖(§6.5)则直接"永久失活",要靠手工拆成 O(n²) 个集成组件。论文在相关章节其实都承认了这些,只是语焉不详地归为"工程问题"。

**最想验证/质疑的具体点**:一是运行时是否(或如何)检验 confined 与 witness——我认为没有,且无法在保持语言无关的同时做到;二是 §5.2.2"HMR 不需要开发者标注 acceptance boundary、与 webpack/Vite 不同"的宣称,和 vendoring 日志里那堆 HMR/Include 竞态补丁并置时显得过于乐观;三是 Theorem 73 的 confluence 在"有失败(§4.3.4)"时被作者自己排除(失败是真实的发散源),那么"把动态系统当静态装配来推理"的承诺,在现实系统里到底覆盖多少执行路径。
