# 作者观点底稿（2026-08-16）

> 本文档是文章作者的原始判断底稿，逐条记录于 2026-08-16 的讨论中，用于后续组织成正式文章。表述尽量保留原意，不在此处展开论证。

## 1. deepseek harness 做好自我迭代的准备了么？

判断：**没有。依然靠人类推动迭代**。即使 agent 可以自己处理、改善插件，依然需要人类的意图驱动。

## 2. deepseek harness 本身是一个什么样的工具 / 产品？

判断：deepseek harness 是一个**套了插件体系的 agent runtime**——agent 该有的东西全部以插件化的方式供应。所以它是一个容易被改造和更改的体系。

与传统的 runtime / OS 不同，它本身并不追求性能的极致性 / 简洁性，它追求的是：

- **边界责任的清晰感**
- 尽量**实时的 harness coding playground**

以做到两件事情：

1. **收敛进行改进时的搜索空间**
2. 尽量把「改进」这件事**自循环**起来（还没做到自驱动）

这两件事的好处：对使用者与开发者，可以快速得到自己想要的改造能力与落地能力——毕竟只要口喷，agent 似乎就可以按照自己想要的方向演化。这确实是一种收益，因为基本上市面上所有的 agent 产品都无非是用另外一个 coding agent 进行修改迭代；而开发迭代的如果是远离场景的开发者，那么真实的 reward 会产生偏移（这不一定是坏事，因为真理总是掌握在少数人手中）。

但同时，又觉得并没有做到极致：

- **核心模块依然需要代码库迭代**（如果你想改进的话）
- **大量的 agent 语义层的约束和上下文控制的规范还是比较空白**的阶段。代码层面的责任清晰，不代表语义层面和功能逻辑层面清晰。
- 如果想要做出更好、更容易迭代的 agent harness，就必须要有**全局视角的迭代机制与分层机制**。这也是为什么从一开始就说**语义层不足**的原因。
- 现在的自我迭代更像是：我提供了工具、提供了报错 / 运转信息了，剩下的模型可以做得很好。但实际上**进程级重启、自我迭代的上下文范畴收敛，是没有完工的**。

## 3. deepseek harness 到底有什么可取之处？代表了什么趋势？

核心产品逻辑已在上节。优势（大概是）：

- **3.1 插件化**——作者更愿意称之为「**领域化**」，因为热重载和领域隔离真的需要这个插件机制么？持怀疑态度。
- **3.2 更贴合 deepseek RL 的 harness 机制**——比如上下文拼装机制与 minimal / code mode。
- **3.3 可以成为各种 harness 的爸爸的潜力**——作者喜欢把插件化称之为「**拟态蠕虫化**」，因为你可以随时把另外一款产品的核心机制变成自己的，如果你想的话。

关于背景判断：崔神和 deepseek 内部应该是从一开始就想下注 **RSI 和自进化**，然后这个方向上应该是分团队进行的。harness 团队更多承担的是**模型以外的 harness 机制**，以及**如何为模型演进提供养料**。

所以趋势上，它代表了：**harness 如何更短、更快、更及时地在场景中意识到问题，以及进行领域性改进的方向**。

## 4. 这么做对么？成立么？能长久下去么？

一句话：事在人为，既然开了这条道，自然会向下走，软件不是静态的。

但隐约有一些隐患，姑且写下来：

- **外围产出动力问题**：虽然说 agent 在自己迭代，但我们依然需要大量的开发者参与（意图与环境提供者），真正有价值的产出还是在外围。怎么搞定大家（不能纯卖流量……）持续产出的动力是最大的问题。尤其是虽然项目是 MIT 开源，但是不允许贡献，参与者也没什么名分。根据崔神的招聘列表，看起来更像是**把插件生态当养料，来健壮自己的产品**（招产品经理不做产品就说不过去了）。而 deepseek 历史上的产品除了模型和一些技术框架外是没有开源或者共享传统的，或者说更像是**开源但并不开放**的状态。**鱼肥果熟进我肚**可能性非常高。
- **熵减消灭可能性**：当我们为 agent 的自我迭代开始划分节点、领域和规范这些事情的时候，本身就是一种外围策略的熵减，其实从第一天起就**灭绝了 agent 自身的可能性**。这也是为什么 deepseek 做 rl 的同事只愿意训练 minimal mode 的原因（这个更第一性原理，最好所有的 harness 都是 agent 自己手搓的）。所以目前提出的这种解决方案会让周边的开发者很开心（不深入的那种），因为有流量又容易上手；但是真实想搓出来 **e2e 的 agent 自我迭代**，还差距很远。
