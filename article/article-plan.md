## 第一问：这是一个什么工具/产品？

**作者主张**：
- 套了插件体系的 agent runtime，agent 该有的东西全插件化供应
- 不追求性能极致/简洁性，追求**边界责任清晰感** + **实时 harness coding playground**
- 两个目的：收敛改进的搜索空间；把改进自循环起来（还没到自驱动）
- 收益：口喷即可按自己方向演化，绕开"远端开发者 reward 偏移"
- 未完工：核心模块仍需代码库迭代；语义层约束与上下文控制规范空白；进程级重启、自迭代上下文范畴收敛未完成

## 第二问：做好自我迭代的准备了么？

**作者主张**：没有。仍然靠人类推动；agent 能改插件，但意图要靠人驱动。

**研究证据**：

| 主张 | 证据位置 |
|---|---|
| agent 铺、人抓错 | iteration-history/human-discovery-timeline.md：六类信号统计（27 revert、99 fix 链、139 快照重录、搏斗日峰值单日 68 提交）、"大改之后必然跟着人类密集纠错"、评审打到 round 14 |
| 意图驱动在人类侧 | model-context/02、05：turn 由 inbox 认领驱动（消息来自人/steer/hook）；goal-round-driver 由人 armed；design-rationale 原则 5（循环只被外部消息推） |
| 已有的自迭代机制盘点 | 原则 10（extensions 元工具）、model-context/14（fiber 级回滚）、cordis/audit-wave3（fuzz 收敛性：fiber 状态机 9750 步零违反——机制层比想象硬） |
| 缺的不是机制是评估闭环 | paper 讨论记录第 14 轮：自迭代 = 假设→改动→观察→保留/丢弃，五样必需品里**归因（日志）与廉价评估（重放）**仓库已有，**保留标准（held-out 评估闸门）没有**；最终结论 6：评估闸门才是胜负手 |

**结论线**：机制底子（改动面、日志、重放）超预期地齐，但"改动之后凭什么保留"没有系统化；没有评估闸门就没有自驱动，只有人驱动的自循环。这与作者"还没做到自驱动"的判断完全一致，且把"意图"具体化为"评估标准 + 目标设定"两个环节都还由人担任。

**需要作者补足**：为什么"人类的意图驱动"是现状而非坏事——材料只证明现状如此，不评价应该怎样。

## 第三问：可取之处与趋势

**作者主张**：
- 3.1 插件化（作者倾向叫"领域化"；对热重载/领域隔离是否真需要插件机制持疑）
- 3.2 更贴合 DeepSeek RL 的 harness 机制（上下文拼装、minimal/code mode）
- 3.3 "harness 的爸爸"潜力 / 拟态蠕虫化
- 背景判断：崔神与内部从一开始下注 RSI/自进化，分团队推进；harness 团队承担模型外的 harness 机制 + 为模型演进提供养料
- 趋势：harness 如何更短更快更及时地在场景中意识到问题、做领域性改进

**研究证据**：

| 主张 | 证据位置 |
|---|---|
| 3.1 怀疑有据 | paper 讨论记录第 13 轮：**耦合是领域属性不是框架属性**，插拔框架不减少耦合只在拆除时暴露；第 11 轮：行业投票是隔离/验证器/引流，没人靠逆操作；audit 三波：框架机制自身成为新耦合源（vendor 补丁日志、W3 缺陷族） |
| 3.1 但统一改动面是真的 | 讨论记录最终定位：Cordis 做好"改动面语法"这一块即可——领域化收益不是热重载而是**一种语言说清楚整个系统** |
| 3.2 RL 贴合 | model-context 全 15 篇：模型可见⟺已记录、请求逐字节可重建（invariant.ts）、snapshot 重放 = 测试集；04 的 code-mode、07 的 native/非 native 部署差异；discussion record 第 14-15 轮把 session log 直接点名成"归因、重建、评估、回滚全部从它派生"的底料 |
| 3.3 拟态蠕虫化 | packages/hooks（Claude Code/Codex 钩子桥 + wire-protocol 库）、design-rationale 原则 2（换 Provider 不动 Consumer）、原则 6（组合决定存在）、paper 讨论记录第 14 轮：改动只有一种表达（组合配置），吞并他者机制 = 把它表达成插件行 |
| 养料论 | model-context/03、10：append-only 日志 + 快照 + 重建不变式 = 天然的模型训练/评估数据面；human-discovery 的六类信号本身就是"人类反馈数据" |

**需要作者补足**：崔神/内部 RSI 下注是作者外部观察与推断（讨论记录开放问题 4 也承认"给已有框架找新市场"属推断），文章里应明确标注是推断而非事实；"领域化"这个命名的展开。

## 第四问：这么做对么？成立么？长久么？

**作者主张**：
- 事在人为，软件不是静态的
- 隐患 1：外围产出动力——意图与环境提供者仍在开发者侧；MIT 但不接受贡献（已验证：CONTRIBUTING.md "cannot accept external pull requests at the moment"）；生态是养料、鱼肥果熟进我肚的风险；DeepSeek 传统上开源但不开放
- 隐患 2：熵减消灭可能性——划分节点/领域/规范本身就是对 agent 自身可能性的灭绝；DeepSeek RL 同事只训练 minimal mode 是第一性原理路线；当前方案让浅层参与者开心（流量 + 上手），但离 e2e 自迭代很远

**研究证据**：

| 主张 | 证据位置 |
|---|---|
| 贡献政策 | 仓库 CONTRIBUTING.md 原文（不接受外部 PR，欢迎 issue 投票、dsh-plugin 生态、博客）——作者判断的实证锚点 |
| 外围价值产出 | human-discovery-timeline：人贡献的是"这个声明真的成立吗"与边角发现；iteration-history：人类侧与 agent 侧的互补分工——意图提供者确实不可被 agent 替代 |
| 熵减消灭可能性 | paper 讨论记录第 15 轮：**收窄表达面反而使过拟合更便宜**；探索边界（表达面）与泛化（评估面）正交——划分节点解决的是搜得动，不解决搜得对，且可能让长尾串联过拟合更快；minimal mode 路线 = 不预设 harness 结构，把全部设计空间留给模型 |
| 离 e2e 自迭代多远 | 讨论记录最终结论 6 + 开放问题 5/6：评估闸门缺失、跨模块归因未经实证、论文完全未涉评估面——三条都是 e2e 的硬缺口 |

**结语可落地的三条**（把"事在人为"具体化）：
1. 改动面已就绪（研究支持：机制层比预期硬，fuzz 收敛）
2. 胜负手在评估面（重放测试集 + held-out 保留标准 + 情节级归因）
3. 生态策略决定它是 harness 的爸爸还是另一个养料池（开源但不开放 vs 拟态蠕虫化的张力）
