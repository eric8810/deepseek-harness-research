# DeepSeek Harness に関する四つの判断

> 日付：2026-08-16。本文は docs/research の研究を踏まえた判断と予測であり、研究記録そのものではない。判断の底稿は [viewpoints-2026-08-16.md](https://github.com/eric8810/deepseek-harness-research/blob/master/article/viewpoints-2026-08-16.md)、構成案は [article-plan.md](https://github.com/eric8810/deepseek-harness-research/blob/master/article/article-plan.md) にある。
>

## 導入：まず結論を先に置く

1. DeepSeek Harness はプラグイン体系を被せた agent runtime である。agent に必要なものはすべてプラグイン化の方式で供給され、境界責任は明確で、しかも実行時に自分自身を直接書き換えられる。それは性能の極致も、簡潔さも追求しない。追求するのは、境界責任の明確さという感覚と、可能な限りリアルタイムな harness coding playground である。
2. それは自己反復の準備ができているのか？**いいえ**。変更の仕組み、ログ、リプレイ、プラグインレベルのロールバックはすべて揃っているが、自己駆動を本当に決める四つがすべて欠けている。**改善の主体性、改善そのものの完全なコンテキスト、自己評価、そして汎化**である。だから今はまだ**自己循環の雛形**と呼ぶべきで、**自己駆動**ではない。
3. その長所は三つある。**領域化**（システム全体に変更方法が一種類しかない）、**DeepSeek RL との適合**（モデルが見る内容はすべてログから再構築でき、スナップショットのリプレイはテストセットに等しく、code mode）、そして**擬態蠕虫化の可能性**（いつでも他製品の中核機構を自分のプラグインとして取り込める）である。
4. ただし二つの隠れた問題がある。**エコシステムの動力**（MIT だがコントリビューションを受け付けない、「魚が肥え果実が熟せば、わが腹に収まる」リスク）と**エントロピー削減の代償**（ノード・領域・規範を区切ることは、初日から agent 自身の可能性を削り取っている）である。
5. 事は人為にあり（成否は人次第）：この道は歩み続けられる。ただし勝敗の分かれ目は変更の仕組みではなく、四つのより柔らかいものにある。改善の主体性、改善そのものの完全なコンテキスト、自己評価、そして汎化である。

## 序論：材料と方法

この記事は 2026-08-15 から 08-16 の二日間にわたる四つの研究に基づく。Cordis のメカニズム研究と三回のセキュリティ監査¹、モデルコンテキストの組み立ての逐項分解⁶、リポジトリの同一 git 履歴の二軸レトロスペクティブ（コードの弧 × 人間の修正パルス）¹⁴、そして時空間合成可能性論文の四モデル読解¹⁷である。材料はいずれも再現可能であり、以下で推測に属する箇所は、その都度個別に明示する。

## 第一の問い：これは何か？──プラグイン体系を被せた agent runtime

### すべてがプラグイン、ループそのものも含めて

DeepSeek Harness は起動時には**空の木**であり、パッチ層の意味論（cordis.yml の patch 行）によってプラグインを一行ずつ積み上げていく。session、agent-loop、system-prompt、tools、llm はいずれもプラグイン行であって、フレームワークの組み込み物ではない³。**ループそのものさえプラグインである**──agent-loop は base bundle 内の一行であり、各ステップの前後にはプラグインが差し込めるイベント発火点が掛けられ、公式のルールは「ループは決して変えない」である⁴。plan mode、goal、todo といった製品機能は、すべて「セッションイベント + 投影 + プロンプト断片 + ツール + コマンド」の五つの平面で組み立てられ、ループは一行も変えられていない。

だから「agent runtime」という性格付けは正確だが、半句を付け足す必要がある。これは **agent に必要なものすべてをプラグイン化の方式で供給する** runtime である。ツールもプラグイン、戦略もプラグイン、信頼境界もプラグイン、製品機能もプラグイン、プラグインツリーを検査・変更する能力そのものさえプラグインである──extensions グループは一揃いの cordis ツールをモデルに公開し、プラグインツリーの列挙、状態の照会、プラグインの定義・実行、停止・削除ができる⁴。harness 全体は一つのものへと組織され、変更には一種類の表現方法しかない¹⁷。

### それは何を追求するか：境界責任の明確さ + リアルタイム coding playground

従来の runtime/OS との分岐点はここにある。従来の runtime は性能の極致、資源スケジューリング、簡潔な抽象を追求する。harness が追求するのは二つのものだ。

**第一に、境界責任の明確さ。** 各能力は「定義 / 実装 / モデル側」の三段階に分割され（Service Definition / Provider / Consumer）、三つの関心事はそれぞれ独立に進化する。方針はツール内の if ではなくイベントリスナーである。信頼境界は独立した層をなす──credentials、identity、workspace は agent 機能と分離される。コンテキスト予算は差し替え可能な方針チェーンである⁴。プラグイン同士の相互作用の方式さえ三種類しかない。強い依存注入、イベントブロードキャスト、オンデマンド取得の三つで、それぞれが一つの結合強度に対応し、明示的に経路を選ぶ²。コードレベルでの責任の帰属は、このフレームワークでは構築されるものであり、自覚に頼るものではない。

**第二に、可能な限りリアルタイムな harness coding playground。** 変更の三つの通路はすべて実行時へ通じる。設定の変更はプラグイン本体の再実行を引き起こす。コードの変更はホットリロードを経由する（旧バージョン破棄、新バージョンはゼロから登録）²。実行時には cordis ツールでプラグインを直接マウント／アンマウントできる。プラグインレベルにはさらにロールバックがある──新バージョンの起動で例外を投げれば旧バージョンへ自動ロールバックし、それに依存するプラグインも自動的に再インストールされる¹²。これが私の言う「harness coding playground」である。走らせながら変更でき、壊せばプラグインレベルで自動的に元へ戻る。

**この二つは二つのことを成すためのものだ。改善時の探索空間を小さくすること、そして「改善」という営みをなるべく自力で回すこと（まだ自動では回せない）。** 前者は前述の構造化された変更だ。システム全体に構造は一種類、変更方法も一種類しかなく、システムはモデルにとって可読である──間違えても構造的なエラーであって、意味論上の水掛け論ではない。探索空間が小さくなればモデルの収束は速い¹⁷。議論中の一言を借りれば「Cordis は『システムをどう変えるか』の構文として使え。安全機構や反復エンジンとして使うな」。後者──自己循環──はまだ自己駆動まで至っておらず、第二の問いで展開する。

### 利益は実在する：口で言うだけで進化する

この設計の利用者への利益は直接的だ。**口で言うだけで、agent は自分が望む方向へ進化してくれるようだ**。欲しい能力を説明すれば、agent はプラグインツリーに新しいプラグイン行を掛け、既存の発火点をリッスンし、さらには cordis ツールで実行時にマウントする──改造への道のりは会話レベルまで短い。

ここに見落とされがちな対比がある。世の中のほぼすべての agent 製品の反復方法は「別の coding agent にコードベースを修正させる」以外にない。そしてコードベースを修正するのが利用場面から遠い開発者なら、真の reward はずれてしまう──開発者が最適化するのは自分が推測した場面であって、場面そのものではない。これは必ずしも悪いことではない（真理は常に少数の手にある）が、harness の設計は**場面の中にいる利用者**を改造者にし得る。コードベース全体を理解する必要はなく、プラグイン行の構文だけを理解すればよい。reward のずれという問題は消えていないが、距離は構造的に縮められている。

### しかし極致には至っていない：三つの未完成箇所

**その一、中核モジュールは依然としてコードベースの反復を必要とする。** agent-loop、session 投影、system-prompt 組み立てといった中核機構を改良したいなら、依然としてリポジトリの流れを通る。`packages/` を変更し、不変条件を通過し、スナップショットテストを通過する。二か月で八百余りの core コミットがあり、七つの段階で中核パッケージは何度も改名・抽出・統合された¹⁵。ファジングテストは、プラグインローダを百パーセント CPU でハングさせる設定の書き方（設定グループをそれ自身の下にマウントする）さえ見つけており、命中率は約 55% で、フレームワークのソースを直すしかない⁵。**フレームワーク機構そのものも上流のコード修正を必要とするソフトウェア**であり、純粋な設定ではない。

**その二、意味層とコンテキスト制御の規範はまだ空白である。** コードレベルでの責任が明確だからといって、意味レベルと機能ロジックレベルが明確なわけではない。二つの直接的証拠がある。07-19 の修正は「不変条件の検査はすべて形状の空回り」と認めた──検査しているのは API 形状であって実在の実行時関係ではない¹⁶。そして「ある変更を残すべきかどうか」の基準は、フレームワークには一言も書かれていない¹⁷。ツール説明をどう書くか、モデルが何のコンテキストを見るか、一度の変更の後に何をもって成功とするか、これらの意味契約は現在、人間のレビューとスナップショット再録に頼っており、体系化された規範ではない。これが、私が最初から**意味層が不足している**と言う理由でもある。責任の明確さは必要条件だが、十分条件ではない。

**その三、プロセスレベルの再起動と自己反復のコンテキスト範囲の収束は完成していない。** プラグインのホットリロードで壊しても自動的に戻せるが、**プロセス再起動にはこの種の後退がない**──起動時の検収を通過できなければ単に起動できず、「前回使えた設定」へ戻る手段もなく、壊れた設定は人間が直すしかない¹²。また、再起動という出来事そのものはモデルに伝えない。再起動が起きたことをコンテキストに入れる仕組みはなく、モデルはせいぜい次ターンの system/tools の差分から自分で推測するしかない¹²。アンマウントの瞬間、キューにあってまだ引き取られていないメッセージは消去される。「自己反復の際にどのコンテキストを持ち越し、どれを捨てるか」の規範はなく、各コントリビューターがそれぞれ「ログを読んで、前回どこまで注入したか自問する」仕組みがあるだけだ。現在の自己反復はむしろ次のようだ。**私はツールを提供し、エラーと稼働情報を提供した。あとはモデルが十分にうまくやれる**──だがプロセスレベルの再起動とコンテキスト範囲の収束という二つの工学的課題は、未完成である。

## 第二の問い：自己反復の準備はできているか？──仕組みはあるが、決定的な四つはまだない

**判断：いいえ。依然として人間が反復を推進している。** agent が自分でプラグインを処理・改善できたとしても、依然として人間の意図による駆動が必要だ。以下、この一文を分解して証明する。

### 既にあるフィードバック能力：多少は見えるが、足りない

harness は agent に自分を観察・デバッグする能力をいくつか与えている。これは事実だ。

- **自分を見られる**：extensions はプラグインツリーをモデルツールとして公開する──プラグインツリーの列挙、各プラグインの状態（承認待ち／実行中／停止）の照会ができる。インターフェースと宣言も直接照会できる⁴。
- **自分を試せる**：モデルは実行時にプラグインを定義・実行・停止・削除できる。動的パッケージの実行結果はコンテキストへ注入される¹³。試して壊してもプラグインレベルのロールバックが下支えする¹²。
- **エラーを聞ける**：ツールエラー、タイムアウト、方針による遮断は、エラーテキストがそのままコンテキストに入る。権限方針が変わったり、ループが詰まったりしても明示的な通知がある¹³。
- **リプレイできる**：セッションログが唯一の事実源であり、モデルが見るすべてのバイトはログからそのまま再構築できる¹¹。

だが「足りないようだ」は正しい。欠けているのは三か所だ。

- **中核障害はモデルに聞こえない**：agent loop 自身が停止しても、エラーはログに書かれて人間とテレメトリが見るだけであり、モデルは次ターンをゼロから始め、説明を得られない¹³。
- **プラグインの装着・取り外しはデフォルトでは黙っている**：何がアンマウントされ、何が置き換えられたか、モデルは次ターンの system/tools の差分から推測するしかない¹³。
- **静かな失敗は人間にすら見えない**：さらに隠れているのは、毎回のホットリロードが**設定を静かにロールバックし得る**ことだ──ファイル、エントリオプション、実行状態の三か所で分岐していても、ログは一切ない⁵。ログにないものは、モデルにはなおさら知りようがない。

より根本的には、これらの観察は**原料であって、判断ではない**。プラグインツリーを見て、エラーを聞いても、どの変更がどの結果を引き起こしたかは分からない。その変更を残すべきかどうかも分からない。完全なループは四段階──観察、原因の特定、善し悪しの判定、保持の決定──だが、今は第一段階しか実体がない。

### 本当に欠けている四つ：主体性、完全なコンテキスト、自己評価、汎化

自己反復 ≠ タスクループ（タスクループは仕事をすることで、自己反復は**自分を変えること**）¹⁷。それは本質的に、モデルが自分の設計空間の上で探索を行い、実際のタスクの成績を判定に使い、有効な変更を保持することである──反復のたびに一つの実験だ。仮説 → 変更 → 観察 → 保持または破棄。

このループを支えるには、重要度順に五つのものが必要だ。ログ（事が起きたとき何が起きたか分かる）、きれいに取り消せる変更単位、変更が狭く構造化された範囲に制限されること、評価が十分に安価であること（リプレイによる）、探索と本番実行の分離。**リポジトリと照らすと、前三つはあり、第四は半分ある**──session log は既製であり、プラグイン行は自然に変更単位となり、システム全体に変更方法は一種類しかなく、スナップショットのリプレイが評価コストを非常に低くする。

だがこれらは依然として変更の仕組みだ。自己駆動できるかを本当に決めるのは、四つのより柔らかいものであり、今はどれもない。

- **主体性**：誰が改善を始めるか。今はすべて人間が始める──目標は人間が設定し、各ループは外部メッセージが駆動する（前節）。
- **完全なコンテキスト**：agent が自分を変えるとき、何を変えたか、なぜ変えたか、どんな状態で変えたかを知る必要がある。プロセスレベルの再起動の後、これらは保証されない──再起動という出来事はモデルに伝わらず、キューにあってまだ引き取られていないメッセージは消去される（第一の問いのその三）。
- **自己評価**：変えた後、自分で善し悪しを判断する。「何をもって保持し、何をもって破棄するか」に体系化された基準はない¹⁷。複数モジュールを同時に変えるときは問題がさらに大きい。各モジュールがそれぞれ勝手に変え、共通の成否基準がなければ、必然的に互いに干渉して発散する。「どのモジュールの変更が成否に寄与したか」をモデル自身に判断させる能力も、まだ検証されていない¹⁷。
- **汎化**：変更は履歴の外でも成立しなければならない。履歴のリプレイをテストセットとして使うのは最低基準にすぎない──いかなる変更も履歴の記録に勝たなければ残れない。リポジトリにはリプレイ（スナップショットテスト）があるが、その判定すらない。その先では、変更をどう表現するかと、変更をどう評価するかは、別々の事柄である¹⁷。表現を狭めることで得られるのは探索の実現可能性であって、正しく探索させることは解決しない。狭めること自体がむしろ過学習を安価にする¹⁷。

この四つのうち、主体性は意図に依り、完全なコンテキストはプロセスレベルの再起動とコンテキスト範囲の収束という工学に依り、自己評価と汎化は評価側の仕組みに依る──いずれも変更の仕組みそのものでは解決できない。

### ループ内での人間の位置：git 履歴は嘘をつかない

評価が人間に依る以上、人間は必然的にループ内に残る。二か月の間に、リポジトリにはこうした痕跡が残った¹⁶。

- まとまった巻き戻し 27 回、連続パッチ 99 回、事後発見的な言い回し 52 回。
- スナップショット再録 139 回（07-30 は単日 25 回）──モデルの出力が変われば人間が署名して確認する。
- 格闘の日：あるフロントエンドモジュールは 07-30 に単日 68 回のコミット、レビューは第 14 ラウンドまで到達し、同日のあるコミットは「revert: restore the reviewer-approved tree」と題された──agent が壊し、人間が木全体を元へ戻した。
- 66 編の障害系の判断ノート。

規則は明らかだ。**agent は敷設を担い、人間は誤りの摘出を担う**。大きな変更の後には必ず人間の集中的な修正が続く（二つのピーク期間 07-27〜08-01 と 08-07〜08-12）。人間の価値はコードを書くことではなく、「この宣言は本当に成立するか」「この隅のケースは試したか」にある。これは harness の欠陥ではない──現状の事実だ。意図駆動の位置もすべて人間側にある。各ループは外部メッセージ（ユーザー入力、外部介入、hook 注入）によって駆動される。goal モードは人間が先に目標を設定して初めて、driver が自動でラウンドを継続する──それはシステム全体で唯一「自動で走り出す」ものであり、目標そのものは人間が設定する¹²。

### 結論：自己循環の雛形はあるが、自己駆動はない

四つをもう一度圧縮する。主体性は目標設定に対応する──何を変えるか、なぜ変えるか。これはおそらく永遠に人間の価値判断であり、agent は自分がどちらの方向へ進化すべきか知らない。完全なコンテキスト、自己評価、汎化は工学側に対応する──いずれも明確な工学的課題だが、一つも完成していない。現在の harness は、自分を見られ、自分を試せ、エラーを聞けるが、四つはどれもない。だから正確な言い方はこうだ。**agent に反復を手伝わせる準備はできているが、agent に自己駆動させる準備はできていない**──後者に欠けているのは変更能力ではなく、主体性、完全なコンテキスト、自己評価、汎化である。

## 第三の問い：長所と趨勢

### 3.1 領域化：プラグイン機構への疑いと、その真の価値

私は「プラグイン化」をむしろ「**領域化**」と呼びたい。なぜなら、疑うに値するのはまさにこういう点だからだ。ホットリロードと領域隔離は、本当にこのプラグイン機構を必要とするのか。

私の疑いには根拠がある。**結合は領域の属性であり、フレームワークの属性ではない**¹⁷──プラグイン機構は結合を減らさず、分解するときにはじめて結合を露呈させる。リポジトリ自身のパッチログが、フレームワーク機構そのものが新たな結合源になったことを証明している。さらに業界の実践を見ると、本番環境で生き残ったホットスワップ／ゼロダウンタイムの方式は、例外なく**逆操作をしない**¹⁷──Erlang は actor で共有メモリを禁止し、Nginx は接続レベルの引き継ぎに依り、K8s は新旧並走のトラフィック誘導に依り、フロントエンドのホットリロードはステートレスなモジュールだけを差し替え、eBPF はバリデータに依る。隔離、バリデータ、トラフィック誘導の三点セットが標準解であり、「効果の宣言 + 逆操作の記述」に依るものは一社もない。ファジングテストがローダとホットリロードで見つけた一連の欠陥（プロセスを百パーセント CPU でハングさせる循環設定、設定の移動後の静かな消失、二つの設定が内容を共有して互いに汚染し合う）は、同じことの別の面だ。プラグイン機構そのものも、バグを生むソフトウェアの一部なのだ⁵。

では harness の領域隔離は実際何に依るのか。能力の三段階分割 + サンドボックス + スコープに依る──これらは**隔離の構築物**であり、プラグイン機構に依存しない（サンドボックスは landlock と e2b を使う）。プラグイン機構が本当に提供するのは別のものだ。**システム全体に変更方法が一種類しかない**こと。システムはモデルに対して可読であり、変更は機械的に検証できる。だから「領域化」の正確な意味はこうだ。領域の境界は隔離の構築物が保証し、領域内の改善はこの統一された変更方法で表現される。ホットリロードはその特性の一つであって、その本質ではない。

### 3.2 DeepSeek RL により密着した harness の仕組み

二つ目の長所は RL 訓練との適合である⁶。

- **モデルが見るすべてのバイトはログから再構築できる**：実行時はバイト単位で検証し、不一致なら即座にエラーを報告する¹¹。つまり、どの実実行も構造化された、再構築可能な訓練／評価サンプルになる──事後的な洗浄は不要で、ログそのものがデータである。
- **スナップショットのリプレイはテストセットに等しい**：session log は、問題の特定、再構築、評価、ロールバックがすべてそこから派生する下地である¹⁷。RL にとって最も高価な資産は評価環境だ。harness は評価環境をリプレイ機構として内蔵している。
- **code mode と minimal 形態**：code mode ブリッジ（コードを直接実行する通路）、ローカルネイティブモードと通常モードのデプロイ差異⁹、ツールリストの code-mode 表現⁷──これらは「モデルが直接コードを書いて実行する」ための構造化された通路であり、RL 訓練でモデルに実実行のフィードバックへ触れさせる路線と一致する。
- **コンテキスト組み立て機構**：system prompt レジストリ、予算方針チェーン、圧縮、ファイルへのオーバーフロー──「モデルに何を、いつ、どれだけ与えるか」は精細な制御面である⁸ ¹⁰。RL 場面では、コンテキスト方針の変更のたびにログへ記録される。これは実験上、極めて価値が高い。

### 3.3 擬態蠕虫化：あらゆる harness の父となる可能性

私はプラグイン化を「**擬態蠕虫化（ミミックワーム化）**」と呼ぶ。望むなら、いつでも別の製品の中核機構を自分のものにできるからだ。これは修辞ではない。リポジトリには既に実例がある──hooks グループは Claude Code/Codex の hook 機構を harness に直接つなぎ込んだ¹⁹。能力の三段階分割は、下層実装の交換を製品側に及ぼさない（モデルを換え、シェルを換え、サンドボックスを換えても、製品側は動かない）。パッチ層は「組み合わせが存在を決める」──外部のいかなる機構も、プラグイン行 + イベントリスナーとして表現できさえすれば、吸収され得る。

変更には一種類の表現方法しかない（組み合わせ設定）から、**プラグイン行として表現できるいかなる機構も吸収範囲内にある**¹⁷。これが「harness の父」の技術的基盤だ。性能が速いからではなく、いかなる競合の中核機構も、この runtime の一つのパッチ行へ取り込めるからだ。それが実現できるかはエコシステムの問題（第四の問いを参照）で、技術上の門は開いている。

### 3.4 趨勢：RSI への賭けと「モデル進化への養料の供給」（本節は推測）

以下は私の内部動機への推測であり、明確に示しておく。**崔神（ディープシーク内部の人物への敬称）と DeepSeek 内部は、当初から RSI（再帰的自己改善）と自己進化に賭けようとしており、この方向はチームを分けて進められているはずだ。harness チームがより多く担うのは、モデル以外の harness 機構と、モデル進化へどう養料を供給するかである。** 証拠は間接的だ。論文の著者所属（北京大学 + DeepSeek-AI）と論文の動機場面（AI による自己改変）。リポジトリが session log、リプレイ、再構築を一級市民にしていること──これらはまさにモデルへ訓練・評価の養料を提供するデータだ。人間の修正が残した痕跡は、本質的に人間のフィードバックデータである。ただし「チームを分けた賭け」「採用の方向性」は外部観察であり、内部では未検証である¹⁷。

そこから導かれる趨勢判断はこうだ。harness が代表する方向は、**より短く、より速く、よりタイムリーに場面の中で問題を認識し、領域的な改善を行う**ことである。「発見 → 突き返し → やり直し」の周期をリポジトリ級からプラグイン行級へ圧縮し、改善の単位を「コードベースを直す」から「組み合わせ設定を変える」へ下げる。これは RSI のロードマップと符合する。モデルの自己改善に必要な最初の地盤は、より強いモデルではなく、**探索でき、はっきり調べられ、戻せる変更の仕組み**である。

## 第四の問い：このやり方は正しいか？成立するか？長続きするか？

先に一言。**事は人為にあり（成否は人次第）。この道を開いた以上、自然と先へ進んでいく。ソフトウェアは静的ではない。** ただし二つの隠れた問題をひとまず書き留めておく。一つはエコシステム側、もう一つは方法論側にある。

### 懸念その一：周辺アウトプットの動力問題

自己反復の宣伝がどんなに派手でも、**本当に価値あるアウトプットは依然として周辺にある**。意図と環境の提供者は開発者、場面の判断は利用者、意味契約の最終裁定は人間だ。問題は、皆にどう継続的にアウトプットしてもらうかだ──単なるトラフィックの切り売りではいけない。

事実の錨が一つある。リポジトリのコントリビューションガイド（CONTRIBUTING.md）¹⁸には「We are sorry that we cannot accept external pull requests at the moment」と原文で書かれている──プロジェクトは MIT でオープンソースだが、**外部コードのコントリビューションを受け付けない**。できるのは issue 投票、`dsh-plugin` トピックを付けたプラグインエコシステム、ブログ執筆だけだ。翻訳すれば、**オープンソースだが、オープンではない**。参加者にコントリビューション権はなく、名分もなく、製品への発言権はなおさらない。（推測：崔の採用リスト──プロダクトマネージャー職を含む──を見ると、むしろプラグインエコシステムを養料として自社製品を鍛えようとしているように見える。プロダクトマネージャーを雇っておいて製品を作らない、では筋が通らない。これは外部観察である。）

もう一層、歴史的観察を重ねる（推測）。DeepSeek のこれまでの製品は、モデルと一部の技術フレームワークを除き、オープンソース化や共有の伝統がない。「オープンソースだがオープンではない」状態に近い。エコシステムのコントリビューターが中核リポジトリに入れず、製品の名分も得られないなら、**魚が肥え果実が熟せば、わが腹に収まる可能性は非常に高い**──周辺が場面、プラグイン、フィードバックをすべて注ぎ込み、果実は公式が摘み取る。短期には無害だ（コミュニティが得るのは始めやすく、トラフィックのあるツール）。長期には枯渇する（継続的アウトプットの動力が存在しない）。

### 懸念その二：エントロピー削減が agent 自身の可能性を絶つ

第二の懸念はより根本的だ。**agent の自己反復のためにノード、領域、規範といったものを区切り始めること自体が、一種の周辺戦略のエントロピー削減であり──初日から agent 自身の可能性を絶っている。**

この代償にはより正確な表現がある。**変更の表現を狭めることは、むしろ過学習を安価にする**¹⁷。変更をどう表現するかと、変更をどう評価するかは、別々の事柄だ。ノードを区切ることで解決するのは前者であり、後者は解決しない。保持の基準が「現在の loop の成功率」だけなら、過学習はリスクではなく、既定の結末になる。つまり、公式が harness をどう組織するかで、モデルの探索空間はその形に刈り込まれる。そしてその空間を刈り込む人は、評価側について確信を持っていない。これが、DeepSeek で RL をやる同僚たちが minimal mode しか訓練したがらない理由でもある（推測、私の外部観察による）。その路線はより第一原理的だ──**できれば harness はすべて agent 自身が手組みするのがよい**。構造を前提とせず、設計空間全体をモデル自身に育てさせるのだ。

だから現行の方案には、ずれた満足感がある。周辺の開発者を（深入りしない範囲で）とても満足させる──トラフィックがあり、始めやすく、口で言うだけで進化する。しかし本気で **e2e の agent 自己反復**を組み上げようとすると、まだ四つ足りない。主体性（誰が改善を始めるか）、完全なコンテキスト（プロセスレベルの再起動とコンテキスト範囲の収束）、自己評価（変更は何をもって保持されるか）、そして汎化（履歴の外でも成立するか）。この四つは、「ノード、領域、規範の区切り」からは一つも自動では生えてこない。

### 二つの懸念の交差点：エコシステム戦略

二つの懸念は実は同じ場所で交わる。**周辺参加者が単なる養料なら、蠕虫化するのは公式チームだけである**──擬態蠕虫化の可能性はコミュニティの仕組みの精華を吸収するために使われ、コミュニティは変更権を得られない。**周辺が本当に変更権と名分を得てはじめて、「harness の父」は成立し得る**──擬態の能力はエコシステム内の多様性によって養われねばならないからだ。オープンソースだがオープンではない、というのはこの道を細める選択である。

## 結語

四つの問いに戻る。私の判断は三つだ。

1. **変更の仕組みは既に整っている。** プラグインレベルのロールバック、バイト単位の再構築、ファジングテスト下での安定は、いずれも仕組みの層そのものが信頼できることを検証している。システム全体に変更方法が一種類しかないことは事実であって、宣伝ではない。これこそ harness が最も過小評価されるべきでない部分だ。
2. **勝敗の分かれ目は四つの柔らかいものにある。主体性、完全なコンテキスト、自己評価、汎化。** 変更の仕組みは既に整っているが、改善を誰が始めるか、改善の際にどのコンテキストを持ち込むか、変えた後どう自分で評価するか、評価した後どう履歴の外でも成立することを保証するか──この四つはどれもない。この四つを先に作り上げた者が、自己駆動の鍵を本当に手にする。それまでは、harness は自己循環の雛形であり、自己駆動のシステムではない。
3. **エコシステム戦略が最大の変数だ。** それが「harness の父」になるか、また一つの養料プールになるかを決める。技術の門は開いており、門の先の道は組織の選択である。

趨勢について。より短く、より速く、よりタイムリーな**領域的改善**は見えている未来だ。本当の**自己駆動**はこのプラグイン機構から自動では生えてこない。それには主体性、完全なコンテキスト、自己評価、汎化の四つが先に作られる必要がある。それまでは、DeepSeek Harness の意義は、人間と agent が同じ方法でシステムを変えられる playground であり──playground の次なる一歩は、この四つがいつ補われるかにかかっている。
