# Four Judgments on DeepSeek Harness

> Date: 2026-08-16. This article is a set of judgments and predictions made after the docs/research study, not the research record itself. The working draft of the judgments is in [viewpoints-2026-08-16.md](https://github.com/eric8810/deepseek-harness-research/blob/master/article/viewpoints-2026-08-16.md), and the organizing plan is in [article-plan.md](https://github.com/eric8810/deepseek-harness-research/blob/master/article/article-plan.md).
>
> Notation convention: statements drawn from source code, git history, repository documentation, and reproducible experiments are treated as **facts**; the author's external observations and inferences about internal motivations are explicitly marked as **inference**. Superscript numbers in the body are source citations, corresponding to the "Sources" list at the end.

## Preamble: conclusions first

1. DeepSeek Harness is an agent runtime wrapped in a plugin system: everything an agent needs is supplied in a plugin-based way, boundary responsibilities are clear, and it can rewrite itself directly at runtime. It does not pursue extreme performance, nor simplicity; it pursues a sense of clear boundary responsibility, and a harness coding playground that is as real-time as possible.
2. Is it ready for self-iteration? **No.** The mechanics of change, logging, replay, and plugin-level rollback are all there, but the four things that truly determine self-driving are all missing: **initiative for improvement, complete context for the improvement itself, self-evaluation, and generalization**. So for now it can only be called a **prototype of self-circulation**, not **self-driven**.
3. It has three merits: **domain-ization** (the whole system has only one way to change), **alignment with DeepSeek RL** (everything the model sees can be reconstructed from the log, snapshot replay equals a test set, code mode), and **the potential for mimic-worming** (turning another product's core mechanism into its own plugin at any time).
4. But there are two hidden risks: **ecosystem momentum** (MIT but not accepting contributions, the risk of "once the fish are fat and the fruit is ripe, they land in my stomach") and **the cost of entropy reduction** (dividing nodes, domains, and norms trims the agent's own possibilities from day one).
5. Human agency decides: this path will continue. But the decisive factor is not the mechanics of change; it is four softer things: initiative for improvement, complete context for the improvement itself, self-evaluation, and generalization.

## Introduction: materials and methods

This article is based on four groups of studies over two days, 2026-08-15 to 08-16: a mechanism study of Cordis and three rounds of security audit¹, an item-by-item dissection of model context assembly⁶, a dual-track review of the same stretch of the repository's git history (code arc × human error-correction pulses)¹⁴, and a four-model study of the spatiotemporal composability paper¹⁷. The materials are all reproducible; wherever something below is inference, I will mark it separately.

## Question one: What is this? — an agent runtime wrapped in a plugin system

### Everything is a plugin, including the loop itself

At startup DeepSeek Harness is an **empty tree**, with plugins assembled onto it line by line through patch-layer semantics (the patch lines of cordis.yml): session, agent-loop, system-prompt, tools, and llm are all plugin lines, not framework built-ins³. Even **the loop itself is a plugin** — agent-loop is one line in the base bundle, with event dispatch points hanging before and after each step for plugins to insert into; the official rule is "never change the loop"⁴. Product features like plan mode, goal, and todo are all assembled from five planes — "session events + projections + prompt segments + tools + commands" — with not a single change to the loop.

So the characterization "agent runtime" is accurate, but it needs a second half: this is a runtime where **everything an agent should have is supplied in a plugin-based way**. Tools are plugins, policies are plugins, trust boundaries are plugins, product features are plugins, and even the ability to inspect and modify the plugin tree is itself a plugin — the extensions group exposes a whole set of cordis tools to the model, letting it list the plugin tree, query status, define and run plugins, and stop and remove plugins⁴. The entire harness is organized as one kind of thing, and change has only one form of expression¹⁷.

### What it pursues: a sense of clear boundary responsibility + a real-time coding playground

The divide from traditional runtime/OS lies here. A traditional runtime pursues extreme performance, resource scheduling, and clean abstractions; a harness pursues two things:

**First, a sense of clear boundary responsibility.** Every capability is split into three segments along "definition / implementation / model-side" (Service Definition / Provider / Consumer), with the three concerns evolving independently; policy is an event listener rather than an if inside a tool; trust boundaries are separated into their own layer — credentials, identity, and workspace are kept apart from agent functionality; the context budget is a pluggable policy chain⁴. Even the ways plugins interact number only three: strong dependency injection, event broadcast, and on-demand retrieval, each corresponding to a coupling strength and an explicit routing choice². Attribution of responsibility at the code level is constructed in this framework, not left to self-discipline.

**Second, a harness coding playground that is as real-time as possible.** All three channels of change lead to the runtime: changing config triggers the plugin body to re-run; changing code goes through hot reload (the old version is destroyed and the new version registers from scratch)²; and at runtime plugins can be mounted/unmounted directly through cordis tools. There is also plugin-level rollback — if the new version throws at startup it is automatically rolled back to the old version, and plugins depending on it are automatically reinstalled¹². This is what I call the "harness coding playground": you can change things while it runs, and if you break something it steps back automatically at the plugin level.

**These two things are meant to accomplish two jobs: shrink the search space when improving, and get "improvement" itself turning as much as possible on its own (automatic turning is not achieved yet).** The former is the structured change described above: the whole system has one structure and one way to change, so the system is readable to the model — getting it wrong produces a structural error, not semantic quibbling; the search space shrinks and the model converges faster¹⁷. To borrow a line from the discussion: "Use Cordis as the grammar for 'how to change the system', not as a safety mechanism or an iteration engine." The latter — self-circulation — has not reached self-driving yet; Question two below elaborates.

### The payoff is real: just say it, and the agent evolves

The payoff of this design is direct for the user: **just say it, and the agent seems to evolve in the direction you want**. You describe a desired capability, and the agent hangs a new plugin line on the plugin tree, listens to an existing dispatch point, or even mounts it at runtime through cordis tools — the path of modification is as short as a conversation turn.

There is an easily overlooked contrast here. Basically every agent product on the market iterates in the same way: "use another coding agent to modify its codebase." But if the person modifying the codebase is a developer far from the usage scenario, the real reward drifts — the developer optimizes the scenario they imagine, not the scenario itself. This is not necessarily a bad thing (the truth is always held by the few), but the harness's design makes **the in-scenario user** a possible modifier: you don't need to understand the whole codebase, only the syntax of a plugin line. The reward-drift problem is not eliminated, but the distance is structurally shortened.

### But it is not taken to the extreme: three unfinished spots

**First, the core modules still require codebase iteration.** If you want to improve the core mechanisms — agent-loop, session projection, system-prompt assembly — you still go through the repository workflow: edit `packages/`, pass the invariants, pass the snapshot tests. Over two months there were more than eight hundred core commits, and across seven phases the core packages were repeatedly renamed, extracted, and merged¹⁵. Fuzzing even found a config pattern that could pin the plugin loader at 100% CPU (mounting a config group under itself), with a hit rate of about 55%, and it could only be fixed by modifying the framework source⁵. **The framework mechanism itself is software that needs upstream code fixes**, not pure configuration.

**Second, the semantic layer and context-control norms are still blank.** Clear responsibility at the code level does not mean clarity at the semantic level or the functional-logic level. Two direct pieces of evidence: a fix on 07-19 admitted that "the invariant checks are all shape no-ops" — they check API shapes, not real runtime relationships¹⁶; and the criterion for "whether a change should be kept" is mentioned nowhere in the framework¹⁷. How tool descriptions are written, what context the model sees, and what counts as success after a change — these semantic contracts currently rely on human review and snapshot re-recording, not systematic norms. This is also why I said from the start that **the semantic layer is insufficient**: clear responsibility is a necessary condition, not a sufficient one.

**Third, process-level restart and context-scope convergence for self-iteration are unfinished.** A broken plugin hot-update can step back automatically, but **a process restart has no such rollback** — if it fails acceptance at startup it simply won't come up, there is no "last known good configuration" to fall back to, and a broken config can only be fixed by hand¹². Moreover, the restart itself never tells the model: there is no mechanism to put "a restart happened" into context, and the model can at best infer it on its own from the system/tools difference in the next round¹². Messages still queued and unclaimed at the moment of unload are discarded; there is no norm for "which context to carry and which to drop during self-iteration", only a mechanism where each contributor "reads the log and asks themselves where the last injection went." Current self-iteration is more like: **I provide the tools, the error reports, and the running information; the model can do the rest quite well** — but process-level restart and context-scope convergence, these two engineering topics, are unfinished.

## Question two: Is it ready for self-iteration? — the mechanics are there, but the decisive four are not

**Judgment: no. Iteration still relies on humans to drive it.** Even if the agent can handle and improve plugins on its own, it still needs human intent to drive it. Below I unpack and prove this statement.

### The feedback abilities it already has: it can see some things, but not enough

The harness does give the agent some ability to observe and debug itself; this is a fact:

- **It can see itself**: extensions exposes the plugin tree as model tools — it can list the plugin tree and query the status of each plugin (pending approval / running / crashed); interfaces and declarations can also be queried directly⁴.
- **It can try itself**: the model can define, run, stop, and remove plugins at runtime; the results of running a dynamic package are injected back into context¹³. If a trial breaks something, plugin-level rollback provides a safety net¹².
- **It can hear errors**: tool errors, timeouts, and policy blocks — the error text goes directly into context; changes to permission policy and a stuck loop also produce explicit reminders¹³.
- **It can replay**: the session log is the single source of truth, and every byte the model sees can be reconstructed verbatim from the log¹¹.

But "it seems insufficient" is right; the gaps are in three places:

- **The model cannot hear core failures**: when the agent loop itself crashes, the error is only written to the log for humans and telemetry; the model starts the next round from zero and gets no explanation¹³.
- **Plugin mount/unmount is silent by default**: who was unmounted and who was replaced can only be guessed by the model from the system/tools difference in the next round¹³.
- **Silent failures are invisible even to humans**: more subtly, every hot reload may **silently roll back config** — file, entry options, and runtime state diverge in three places, with no logging at all⁵. What is not logged, the model has even less way to know.

More fundamentally: these observations are **raw material, not judgment**. Seeing the plugin tree and hearing errors does not equal knowing which change caused which result, nor knowing whether a given change should be kept. The full loop has four steps — observe, locate the cause, judge good or bad, decide to keep — and only the first step is currently concrete.

### The four things genuinely missing: initiative, complete context, self-evaluation, generalization

Self-iteration ≠ task loop (a task loop is doing work; self-iteration is **changing oneself**)¹⁷. It is essentially the model searching over its own design space, judging by performance on real tasks, and keeping effective changes — each iteration is an experiment: hypothesis → change → observe → keep or discard.

Supporting this loop requires five things, in order of importance: a log (so you know what happened when something goes wrong), change units that can be cleanly reverted, changes restricted to a narrow and structured range, evaluation cheap enough (via replay), and separation between search and production runs. **Checking against the repository: the first three are all present, and the fourth is half present** — the session log is already there, a plugin line is naturally a change unit, the whole system has only one way to change, and snapshot replay makes evaluation cheap.

But all of these are still the mechanics of change. What truly determines whether it can self-drive are four softer things, none of which exists yet:

- **Initiative**: who initiates improvement. For now it is entirely initiated by humans — the goal is human-set, and every round of the loop is pushed by an external message (previous section).
- **Complete context**: when the agent changes itself, it needs to know what it changed, why, and in what state. After a process-level restart none of this is guaranteed — the restart itself never tells the model, and queued, unclaimed messages are discarded (Question one, item three).
- **Self-evaluation**: after a change, judging good or bad on its own. There is no systematic criterion for "why keep, why discard"¹⁷; the problem is worse when several modules are changed together, since each module changes on its own with no shared success/failure criterion, inevitably interfering and diverging; whether the model can itself judge "which module's change contributed to success or failure" has not been verified¹⁷.
- **Generalization**: a change must hold beyond history. Using historical replay as a test set is only the minimum bar — any change must beat the historical record to be kept, and the repository has replay (snapshot tests), but not even this judgment. Going further up, how a change is expressed and how it is evaluated are two separate matters¹⁷: narrowing the expression buys search feasibility, not searching correctly; the narrowing itself actually makes overfitting cheaper¹⁷.

Among these four, initiative depends on intent, complete context depends on the engineering of process-level restart and context-scope convergence, and self-evaluation and generalization depend on the evaluation-side mechanisms — none of these can be solved by the mechanics of change itself.

### The human's place in the loop: git history does not lie

Since evaluation relies on humans, humans necessarily remain in the loop. Over two months, the repository left traces like these¹⁶:

- 27 whole-block reverts, 99 consecutive patches, and 52 "discovered afterwards" wordings;
- 139 snapshot re-recordings (25 in a single day on 07-30) — when model output changes, a human must sign off;
- Fight days: one frontend module had 68 commits in a single day on 07-30, with review reaching round 14, and a commit the same day titled "revert: restore the reviewer-approved tree" — the agent broke it, and a human restored the whole tree;
- 66 failure-type decision notes.

The pattern is clear: **the agent does the paving, and the human catches the mistakes**; big changes are inevitably followed by dense human error-correction (two peak spans, 07-27~08-01 and 08-07~08-12). The human's value is not in writing code but in "does this claim really hold" and "have you tried this corner case." This is not a flaw of the harness — it is the fact of the present state. The seat of intent-driving is also entirely on the human side: every round of the loop is pushed by an external message (user input, external intervention, hook injection); goal mode requires a human to first set the goal before the driver auto-continues the round — it is the only thing in the whole system that "starts running by itself," and the goal itself is human-set¹².

### Conclusion: the prototype of self-circulation exists; self-driving does not

Compressing the four again: initiative corresponds to goal-setting — what to change and why; this may forever be a human value judgment, since the agent does not know which direction it should evolve in; complete context, self-evaluation, and generalization correspond to the engineering side — all clearly engineering topics, but none of them is finished. The current harness: it can see itself, try itself, and hear errors, and it has none of the four. So the precise statement is: **it is ready for the agent to assist iteration, not ready for the agent to self-drive** — what the latter lacks is not change capability but initiative, complete context, self-evaluation, and generalization.

## Question three: merits and trends

### 3.1 Domain-ization: doubts about the plugin mechanism, and its real value

I prefer to call "plugin-ization" "**domain-ization**", because what is actually worth doubting is: do hot reload and domain isolation really require this plugin mechanism?

My doubts have a basis. **Coupling is a property of the domain, not of the framework**¹⁷ — a plug-in/plug-out framework does not reduce coupling, it only exposes coupling when things are dismantled; the repository's own patch log proves the framework mechanism itself has become a new source of coupling. Look again at industry practice: the hot-swap / zero-downtime schemes that survive in production uniformly **do not do reverse operations**¹⁷ — Erlang relies on actors to forbid shared memory, Nginx on connection-level handoff, K8s on running old and new side by side and shifting traffic, frontend hot reload on hot-swapping only stateless modules, and eBPF on a verifier. Isolation, verifier, and traffic-shifting — this three-piece set is the standard answer, and none of them relies on "declaring effects + writing reverse operations." The family of defects fuzzing found in the loader and hot reload (circular config that can pin the process at 100% CPU, config silently lost after being moved, two configs sharing content that pollute each other) is the other face of the same thing: the plugin mechanism itself is also a piece of software that can have bugs⁵.

So what does the harness's domain isolation actually rest on? It rests on the three-segment split of capabilities + sandbox + scope — these are the **constructs of isolation**, and they do not depend on the plugin mechanism (the sandbox uses landlock and e2b). What the plugin mechanism really provides is another thing: **the whole system has only one way to change**. The system is readable to the model, and changes are mechanically verifiable. So the precise meaning of "domain-ization" is: domain boundaries are guaranteed by isolation constructs, and improvement within a domain is expressed through this unified way of changing. Hot reload is a feature of it, not its essence.

### 3.2 A harness mechanism more aligned with DeepSeek RL

The second merit is its alignment with RL training⁶:

- **Every byte the model sees can be reconstructed from the log**: the runtime verifies byte by byte and errors out directly on any mismatch¹¹. This means any single real run is a structured, reconstructible training/evaluation sample — no post-hoc cleaning needed; the log itself is the data.
- **Snapshot replay equals a test set**: the session log is the substrate from which problem localization, reconstruction, evaluation, and rollback are all derived¹⁷. The most expensive asset in RL is the evaluation environment; the harness builds the evaluation environment into a replay mechanism.
- **Code mode and the minimal form**: the code-mode bridge (a channel for running code directly), the deployment differences among local native mode and the regular mode⁹, and the code-mode presentation of the tool list⁷ — these are structured channels reserved for "the model writes code and executes it directly," consistent with the RL-training route of letting the model touch real execution feedback.
- **The context-assembly mechanism**: the system-prompt registry, the budget policy chain, compaction, and overflow-to-file — "what to feed the model, when, and how much" is a finely controllable surface⁸ ¹⁰. In an RL scenario every change to the context policy is recorded in the log, which is extremely valuable experimentally.

### 3.3 Mimic-worming: the potential to become the father of all harnesses

I call plugin-ization "**mimic-worming**": you can at any time turn another product's core mechanism into your own, if you want to. This is not rhetoric — there are already instances in the repository: the hooks group plugged the hook mechanisms of Claude Code/Codex directly into the harness¹⁹; the three-segment split of capabilities lets you swap the underlying implementation without touching the product side (swap the model, swap the shell, swap the sandbox — the product side stays put); and the patch layer makes "composition decide existence" — any external mechanism, as long as it can be expressed as a plugin line + event listener, can be absorbed.

Because change has only one form of expression (compositional configuration), **any mechanism expressible as a plugin line is within absorption range**¹⁷. This is the technical basis for "the father of all harnesses": not being faster, but the fact that any competitor's core mechanism can be folded into a single patch line of this runtime. Whether it can actually be done is an ecosystem question (see Question four); the technical door is open.

### 3.4 Trend: the RSI bet and "providing nourishment for model evolution" (this section is inference)

The following is my inference about internal motivations, clearly marked: **from the very beginning, Cui-shen (a reverential community nickname for a DeepSeek insider) and DeepSeek internally probably wanted to bet on RSI (recursive self-improvement) and self-evolution, with this direction pursued by separate teams; the harness team takes on more of the harness mechanisms outside the model, and how to provide nourishment for model evolution.** The evidence is indirect: the paper's author affiliations (Peking University + DeepSeek-AI) and its motivation scenario (AI self-modification); the repository making session log, replay, and reconstruction into first-class citizens — exactly the data that provides training and evaluation nourishment for the model; the traces left by human error-correction are essentially human feedback data. But "separate-team bets" and "hiring orientation" are external observations, not internally confirmed¹⁷.

The trend judgment drawn from this: the direction the harness represents is **becoming aware of problems in-scenario more briefly, faster, and more promptly, and making domain-level improvements**. It compresses the "discover → send back → redo" cycle from the repository level to the plugin-line level, and lowers the improvement unit from "change the codebase" to "change the compositional configuration." This matches the RSI roadmap: the first foundation block model self-improvement needs is not a stronger model, but a **change mechanism that makes search feasible, inspection clear, and rollback possible**.

## Question four: Is doing this right? Does it hold? Will it last?

Let me give one line first: **it's up to people — since this path has been opened, it will naturally go forward; software is not static.** But two hidden risks I'll write down for now, one on the ecosystem side and one on the methodology side.

### Hidden risk one: the motivation problem of peripheral output

No matter how loud the self-iteration pitch, **the truly valuable output still lies at the periphery**: the providers of intent and environment are developers, scenario judgment belongs to users, and the final arbiter of semantic contracts is humans. The problem is how to keep everyone producing — it can't just sell traffic.

There is one factual anchor: the repository contribution guide (CONTRIBUTING.md)¹⁸ says verbatim "We are sorry that we cannot accept external pull requests at the moment" — the project is MIT open source, but it **does not accept external code contributions**; all you can do is vote on issues, build plugins in the ecosystem tagged `dsh-plugin`, and write blogs. Translated: **open source, but not open**. Participants have no contribution rights and no credit, let alone a say in the product. (Inference: judging from Cui's hiring list — including a product-manager position — it looks more like the plugin ecosystem is being treated as nourishment to strengthen their own product; hiring a product manager without building a product would be hard to explain. This is an external observation.)

Layer one more historical observation on top (inference): aside from models and some technical frameworks, DeepSeek's past products have no tradition of open sourcing or sharing, more like a state of "open source but not open." If ecosystem contributors can neither get into the core repository nor obtain product credit, then **the possibility of "once the fish are fat and the fruit is ripe, they land in my stomach" is very high** — the periphery feeds in scenarios, plugins, and feedback, and the fruit is picked by the official side. Harmless in the short term (the community gets a tool that's quick to start and has traffic), but it will dry up in the long term (the motivation for sustained output is absent).

### Hidden risk two: entropy reduction kills the agent's own possibilities

The second hidden risk is more fundamental. **When we start dividing nodes, domains, and norms for the agent's self-iteration, this itself is a kind of entropy reduction in the peripheral strategy — it extinguishes the agent's own possibilities from day one.**

This cost has a more precise statement: **narrowing the expression of change actually makes overfitting cheaper**¹⁷. How a change is expressed and how it is evaluated are two separate matters: dividing nodes solves the former, not the latter; if the only retention criterion is "the success rate of the current loop," then overfitting is not a risk but the default outcome. That is, however the official side organizes the harness, the model's search space is pruned to match; and the person doing the pruning has no confidence on the evaluation side. This is also why DeepSeek's RL colleagues are only willing to train minimal mode (inference, from my external observation): that route is more first-principles — **ideally all harnesses are hand-built by the agent itself**, with no preset structure, leaving the entire design space for the model to grow on its own.

So the current approach has a misplaced sense of satisfaction: it makes peripheral developers happy (the shallow kind) — traffic, easy to start, and evolution just by talking; but to actually hand-build **end-to-end agent self-iteration**, four things are still missing: initiative (who initiates improvement), complete context (process-level restart and context-scope convergence), self-evaluation (why a change is kept), and generalization (holding beyond history). None of these four will grow out of "dividing nodes, domains, and norms" on its own.

### Where the two hidden risks meet: ecosystem strategy

The two hidden risks actually converge in the same place: **if peripheral participants are only nourishment, only the official team gets worm-ified** — the mimic-worming potential will be used to absorb the essence of community mechanisms, while the community gets no right to change; **if the periphery truly gains the right to change and credit, "the father of all harnesses" can hold** — because the mimicry capability must be fed by the diversity within the ecosystem. Open source but not open is a choice that narrows this path.

## Conclusion

Returning to the four questions, my judgment comes down to three points:

1. **The mechanics of change are ready.** Plugin-level rollback, byte-for-byte reconstruction, and stability under fuzzing all verify that the mechanism layer itself is reliable. The fact that the whole system has only one way to change is true, not marketing. This is also the part of the harness least deserving of underestimation.
2. **The decisive factor is the four soft things: initiative, complete context, self-evaluation, and generalization.** The mechanics of change are ready, but who initiates improvement, what context is carried during improvement, how to evaluate it yourself after changing, and how to ensure it holds beyond history — none of these four exists yet. Whoever builds these four first truly holds the key to self-driving. Until then, the harness is a prototype of self-circulation, not a self-driving system.
3. **Ecosystem strategy is the biggest variable.** It decides whether this is the father of all harnesses or just another nourishment pool. The technical door is open; the road behind the door is an organizational choice.

On trends: briefer, faster, more prompt **domain-level improvement** is the visible future; true **self-driving** will not grow out of this plugin mechanism on its own — it requires initiative, complete context, self-evaluation, and generalization to be built first. Until then, DeepSeek Harness's significance is a playground where humans and agents can both change the system in the same way — and the playground's next stop depends on when these four things are filled in.
