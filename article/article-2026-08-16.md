# 关于 DeepSeek Harness 的四个判断

> 日期：2026-08-16。本文是 docs/research 研究之后的判断与预测，不是研究记录本身。判断底稿见 [viewpoints-2026-08-16.md](https://github.com/eric8810/deepseek-harness-research/blob/master/article/viewpoints-2026-08-16.md)，组织方案见 [article-plan.md](https://github.com/eric8810/deepseek-harness-research/blob/master/article/article-plan.md)。
>
> 标注约定：凡属源码、git 历史、仓库文档、可复现实验的陈述，视为**事实**；凡属作者外部观察、对内部动机的推测，明确标注为**推断**。正文中的上标数字为来源标注，对应文末「来源」清单。

## 导语：先把结论放在前面

1. DeepSeek Harness 是一个套了插件体系的 agent runtime：agent 该有的东西全部以插件化的方式供应，边界责任清晰，并且可以在运行时直接改写自己。它不追求性能极致，也不追求简洁，它追求的是边界责任的清晰感，和尽量实时的 harness coding playground。
2. 它做好自我迭代的准备了么？**没有**。改动的机制、日志、回放、插件级回滚这些都有了，但真正决定自驱动的四样都缺：**改进的主动性、改进本身的完整上下文、自评估、以及泛化**。所以现在只能叫**自循环的雏形**，不是**自驱动**。
3. 它的可取之处有三：**领域化**（整个系统只有一种改动方式）、**与 DeepSeek RL 的贴合**（模型看到的内容都能从日志重建、快照回放等于测试集、code mode）、以及**拟态蠕虫化的潜力**（随时把另一款产品的核心机制吞成自己的插件）。
4. 但有两个隐患：**生态动力**（MIT 但不接受贡献，「鱼肥果熟进我肚」的风险）与**熵减代价**（划分节点、领域、规范，从第一天起就在削减 agent 自身的可能性）。
5. 事在人为：这条路会走下去。但胜负手不在改动的机制，在四样更软的东西：改进的主动性、改进本身的完整上下文、自评估、以及泛化。

## 引言：材料与方法

这篇文章基于 2026-08-15 至 08-16 两天的四组研究：对 Cordis 的机制研究和三轮安全审计¹、模型上下文拼装的逐项拆解⁶、仓库同一段 git 历史的双轨复盘（代码弧线 × 人类纠错脉冲）¹⁴、以及时空可组合性论文的四模型研读¹⁷。材料都是可复现的，下文凡属推断的地方，我会单独标出来。

## 第一问：这是什么？——一个套了插件体系的 agent runtime

### 一切皆插件，包括循环本身

DeepSeek Harness 启动时是一片**空树**，通过补丁层语义（cordis.yml 的 patch 行）把插件逐行拼上去：session、agent-loop、system-prompt、tools、llm 都是插件行，不是框架内建物³。甚至**循环本身也是插件**——agent-loop 是 base bundle 里的一行，每一步前后都挂着事件分发点供插件插入，官方规则是「绝不改循环」⁴。plan mode、goal、todo 这些产品功能，全部由「会话事件 + 投影 + 提示词段 + 工具 + 命令」五个平面拼成，循环一行没改。

所以「agent runtime」这个定性是准确的，但要补上半句：这是一个**agent 该有的东西全部以插件化方式供应**的 runtime。工具是插件、策略是插件、信任边界是插件、产品功能是插件、连检视和修改插件树的能力本身也是插件——extensions 组把一整套 cordis 工具暴露给模型，可以列出插件树、查询状态、定义和运行插件、停止和移除插件⁴。整个 harness 被组织成一种东西，改动只有一种表达方式¹⁷。

### 它追求什么：边界责任清晰感 + 实时 coding playground

与传统 runtime/OS 的分野在这里。传统 runtime 追求性能极致、资源调度、简洁抽象；harness 追求的是两样东西：

**第一，边界责任的清晰感。** 每个能力都按「定义 / 实现 / 模型侧」三段拆分（Service Definition / Provider / Consumer），三个关注点各自独立演化；策略是事件监听器而不是工具里的 if；信任边界独立成层——credentials、identity、workspace 与 agent 功能分开；上下文预算是可插拔的策略链⁴。连插件之间的交互方式也只有三种：强依赖注入、事件广播、按需获取，各自对应一种耦合强度，显式选路²。代码层面的责任归属，在这个框架里是构造出来的，不是靠自觉。

**第二，尽量实时的 harness coding playground。** 改动的三条通道都通向运行时：改配置触发插件体重跑；改代码走热重载（旧版本销毁、新版本从零注册）²；运行时通过 cordis 工具直接挂载/卸载插件。插件级还有回滚——新版本启动抛错自动回滚旧版本、依赖它的插件跟着自动重装¹²。这就是我说的「harness coding playground」：你可以边跑边改，改坏了在插件级自动退回来。

**这两样东西要干两件事：让改进时的搜索空间变小，让「改进」这件事尽量自己转起来（还没做到自动转）。** 前者就是前面说的结构化改动：整个系统只有一种结构、一种改法，系统对模型来说是可读的——改错了是结构性的报错，而不是语义性的扯皮；搜索空间变小，模型收敛更快¹⁷。用讨论中的一句话说：「把 Cordis 当『怎么改系统』的语法用，别当安全机制或迭代引擎用。」后者——自循环——还没做到自驱动，下文第二问展开。

### 收益是真实的：口喷即可演化

这个设计的收益对使用者是直接的：**只要口喷，agent 似乎就可以按照自己想要的方向演化**。你描述一个想要的能力，agent 在插件树里挂一个新的插件行、监听既有分发点、甚至用 cordis 工具运行时挂载——改造的路径短到对话级。

这里有一个容易被忽略的对比。基本上市面上所有的 agent 产品，迭代方式都无非是「用另外一个 coding agent 去修改它的代码库」。而修改代码库的如果是远离使用场景的开发者，真实的 reward 就会产生偏移——开发者优化的是自己猜想的场景，不是场景本身。这不一定是坏事（真理总是掌握在少数人手中），但 harness 的设计让**场景内的使用者**成为可能的改造者：你不需要理解整个代码库，只需要理解插件行的语法。reward 偏移的问题没有被消灭，但被结构性地缩短了距离。

### 但没有做到极致：三处未完工

**其一，核心模块依然需要代码库迭代。** 你想改进 agent-loop、session 投影、system-prompt 组装这些核心机制，走的仍然是仓库流程：改 `packages/`、过不变式、过快照测试。两个月八百多条 core 提交，七个阶段里核心包被反复重命名、抽出、合并¹⁵。模糊测试甚至找到一个能让插件加载器百分之百 CPU 挂死的配置写法（把一个配置组挂到它自己下面），命中率约 55%，只能改框架源码修⁵。**框架机制本身也是需要上游代码修复的软件**，不是纯配置。

**其二，语义层与上下文控制规范还是空白。** 代码层面的责任清晰，不代表语义层面和功能逻辑层面清晰。两个直接证据：07-19 的一次修正承认「不变量检查全是形状空转」——检查的是 API 形状而非真实运行时关系¹⁶；而「一条改动该不该保留」的标准，框架里只字未提¹⁷。工具描述怎么写、模型看到什么上下文、一次改动之后凭什么算成功，这些语义契约目前靠的是人类的评审与快照重录，而不是系统化的规范。这也是为什么我从一开始就说**语义层不足**：责任清晰是必要条件，但不是充分条件。

**其三，进程级重启与自迭代的上下文范畴收敛没有完工。** 插件热更新改坏了可以自动退回去，**进程重启没有这种回退**——启动时验收不过就直接起不来，也没有「上一次好用的配置」可以退回，坏配置只能靠人改回来¹²。另外，重启这件事本身不会告诉模型：没有任何机制把「重启发生了」放进上下文，模型最多从下一轮的 system/tools 差异里自己推断¹²。卸载瞬间排队中还没被认领的消息会被清空；「自迭代时哪些上下文该带、哪些该丢」没有规范，只有各贡献者各自「读日志自问上次注入到哪了」的机制。现在的自我迭代更像是：**我提供了工具、提供了报错与运转信息，剩下的模型可以做得很好了**——但进程级重启和上下文范畴收敛这两个工程课题，是没有完工的。

## 第二问：做好自我迭代的准备了么？——机制有了，决定性的四样还没有

**判断：没有。依然靠人类推动迭代。** 即使 agent 可以自己处理、改善插件，依然需要人类的意图驱动。下面把这句话拆开证明。

### 已有的反馈能力：能看见一些，但不够

harness 确实给了 agent 一些观察与调试自己的能力，这是事实：

- **能看自己**：extensions 把插件树暴露成模型工具——可以列出插件树、查每个插件的状态（待审批/运行中/挂掉了）；接口和声明也能直接查⁴。
- **能试自己**：模型可以在运行时定义、运行、停掉、移除插件；动态包跑完的结果会注入回上下文¹³。试坏了有插件级回滚兜底¹²。
- **能听报错**：工具报错、超时、被策略拦下，错误文本会直接进上下文；权限策略变了、循环卡住了也有显式提醒¹³。
- **能回放**：会话日志是唯一的事实来源，模型看到的每个字节都能从日志原样重建¹¹。

但「似乎不够」是对的，缺口在三个地方：

- **核心故障模型听不到**：agent loop 自己挂了，错误只写进日志给人和遥测看，模型下一回合从零开始，得不到解释¹³。
- **插件装卸默认不吭声**：谁被卸载了、谁被替换了，模型只能从下一轮 system/tools 的差异里猜¹³。
- **静默失败连人都看不见**：更隐蔽的是，每次热重载可能**静默回滚配置**——文件、入口选项、运行态三处分叉，没有任何日志⁵。没有日志的东西，模型更无从知道。

更根本的：这些观察是**原料，不是判断**。看到插件树、听到报错，不等于知道哪次改动导致了哪个结果；也不等于知道这条改动该不该留。完整的回路是四步——观察、定位原因、判定好坏、决定保留——现在只有第一步是实的。

### 真正缺的四样：主动性、完整上下文、自评估、泛化

自迭代 ≠ 任务循环（任务循环是干活，自迭代是**改自己**）¹⁷。它本质上是模型在自己的设计空间上做搜索，用真实任务的表现作为评判，保留有效改动——每次迭代是一次实验：假设 → 改动 → 观察 → 保留或丢弃。

支撑这个循环需要五样东西，按重要性：日志（出了事知道发生了什么）、能干净撤销的改动单位、改动被限制在窄而结构化的范围里、评估足够廉价（靠回放）、搜索和正式运行分开。**对照仓库：前三样都有，第四样有了一半**——session log 是现成的，插件行天然就是改动单位，整个系统只有一种改动方式，快照回放让评估成本很低。

但这些都还是改动的机制。真正决定能不能自驱动的，是四样更软的东西，现在一样都没有：

- **主动性**：谁发起改进。现在全部由人发起——目标是人设的，每一轮循环由外部消息推动（上一节）。
- **完整上下文**：agent 改自己的时候，需要知道自己改了什么、为什么改、在什么状态下改的。进程级重启之后这些没有保障——重启这件事不会告诉模型，排队中还没被认领的消息会被清空（第一问其三）。
- **自评估**：改完之后自己判断好坏。「凭什么保留、凭什么丢弃」没有任何系统化的标准¹⁷；多个模块一起改的时候问题更大，各模块各改各的、没有一个共同的成败标准，必然互相干扰而发散；让模型自己判断「哪个模块的改动贡献了成败」，这个能力也还没有被验证¹⁷。
- **泛化**：改动在历史之外也要成立。把历史回放当测试集只是最低标准——任何改动都必须赢过历史记录才能留下来，仓库有回放（快照测试），但连这个判定都没有。再往上，改动怎么表达，和改动怎么评估，是两件分开的事情¹⁷：把表达收窄，换来的是搜索可行，不解决搜得对；收窄本身反而让过拟合变得更便宜¹⁷。

这四样里，主动性靠意图，完整上下文靠进程级重启和上下文范畴收敛的工程，自评估和泛化靠评估这一侧的机制——都不是改动的机制本身能解决的。

### 人类在循环里的位置：git 历史不会说谎

既然评估靠人，人类就必然留在循环里。两个月内，仓库留下了这样的痕迹¹⁶：

- 整块回退 27 次、连续修补 99 次、事后发现类措辞 52 次；
- 快照重录 139 次（07-30 单日 25 次）——模型输出变了要人签字确认；
- 搏斗日：某个前端模块 07-30 单日 68 次提交，评审打到第 14 轮，同天一次提交叫「revert: restore the reviewer-approved tree」——agent 改崩了，人把整棵树还原；
- 66 篇故障类决策笔记。

规律很清楚：**agent 负责铺，人负责抓错**；大改之后必然跟着人类的密集纠错（两个峰值段 07-27~08-01 与 08-07~08-12）。人类的价值不在写代码，在「这个声明真的成立吗」和「这个边角你试过吗」。这不是 harness 的缺陷——这是现状的事实。意图驱动的位置也全在人侧：每一轮循环都由外部消息推动（用户输入、外部干预、hook 注入）；goal 模式要人先设定目标，driver 才会自动续轮——它是整个系统里唯一「自动开跑」的东西，而目标本身是人设的¹²。

### 结论：自循环的雏形有了，自驱动没有

把四样再压缩一下：主动性对应目标设定——改什么、为什么改，这也许永远是人类的价值判断，agent 不知道自己该往哪个方向演化；完整上下文、自评估、泛化对应工程侧——都是明确的工程课题，但一个都还没完工。现在的 harness：能看自己、能试自己、能听报错，四样一样都没有。所以准确的说法是：**它做好了让 agent 协助迭代的准备，没有做好让 agent 自驱动的准备**——后者缺的不是改动能力，是主动性、完整上下文、自评估和泛化。

## 第三问：可取之处与趋势

### 3.1 领域化：对插件机制的怀疑，和它真正的价值

我更愿意把「插件化」叫作「**领域化**」，因为值得怀疑的恰恰是：热重载和领域隔离真的需要这套插件机制吗？

我的怀疑有依据。**耦合是领域属性，不是框架属性**¹⁷——插拔框架不减少耦合，只在拆除时暴露耦合；仓库自己的补丁日志证明框架机制本身成了新的耦合源。再看行业实践：生产环境活下来的热切换/零停机方案，清一色**不做逆操作**¹⁷——Erlang 靠 actor 禁止共享内存、Nginx 靠连接级交接、K8s 靠新旧并排引流、前端热重载只热替换无状态模块、eBPF 靠验证器。隔离、验证器、引流三件套是标准答案，没有一家靠「声明效应 + 写逆操作」。模糊测试在加载器和热重载上找到的一族缺陷（能让进程百分之百 CPU 挂死的循环配置、配置搬移后静默丢失、两份配置共享内容导致互相污染）是同一件事的另一面：插件机制本身也是一块会出 bug 的软件⁵。

那么 harness 的领域隔离实际靠什么？靠的是能力的三段拆分 + 沙箱 + 作用域——这些是**隔离的构造**，不依赖插件机制（沙箱用 landlock 和 e2b）。插件机制真正提供的是另一件东西：**整个系统只有一种改动方式**。系统对模型可读，改动机械可验证。所以「领域化」的准确含义是：领域边界靠隔离构造保证，领域内的改进靠这种统一的改动方式表达。热重载是它的一个特性，不是它的本质。

### 3.2 更贴合 DeepSeek RL 的 harness 机制

第二个可取之处是与 RL 训练的贴合⁶：

- **模型看到的每个字节都能从日志重建**：运行时会逐字节校验，不一致直接报错¹¹。这意味着任何一次真实运行都是结构化的、可重建的训练/评估样本——不用事后清洗，日志本身就是数据。
- **快照回放等于测试集**：session log 是定位问题、重建、评估、回滚全部从它派生的底料¹⁷。RL 最贵的资产是评估环境；harness 把评估环境内建成了回放机制。
- **code mode 与 minimal 形态**：code mode 桥（直接跑代码的通道）、本地原生模式和常规模式的部署差异⁹、工具列表的 code-mode 呈现⁷——这些是给「模型直接写代码执行」留的结构化通道，与 RL 训练中让模型接触真实执行反馈的路线一致。
- **上下文拼装机制**：system prompt 注册表、预算策略链、压缩、溢出到文件——「给模型喂什么、什么时候喂、喂多少」是精细控制面⁸ ¹⁰。RL 场景里上下文策略的每次变动都会被记录进日志，这在实验上极有价值。

### 3.3 拟态蠕虫化：成为各种 harness 的爸爸的潜力

我把插件化叫作「**拟态蠕虫化**」：你可以随时把另外一款产品的核心机制变成自己的，如果你想的话。这不是修辞，仓库里已有实例——hooks 组把 Claude Code/Codex 的 hook 机制直接接进了 harness¹⁹；能力的三段拆分让换底层实现不动产品侧（换模型、换 shell、换沙箱，产品侧不动）；补丁层让「组合决定存在」——任何外部机制只要能被表达成插件行 + 事件监听，就能被吸收。

因为改动只有一种表达方式（组合配置），**任何可表达为插件行的机制都在吸收范围内**¹⁷。这就是「harness 的爸爸」的技术基础：不是性能更快，而是任何竞品的核心机制都可以被收进这个 runtime 的一个补丁行。能不能做到是生态问题（见第四问），技术上的门是开着的。

### 3.4 趋势：RSI 下注与「为模型演进提供养料」（本段为推断）

以下是我对内部动机的推断，标注清楚：**崔神和 DeepSeek 内部应该是从一开始就想下注 RSI（递归自我改进）和自进化，这个方向分团队进行；harness 团队更多承担的是模型以外的 harness 机制，以及如何为模型演进提供养料。** 证据是间接的：论文作者单位（北大 + DeepSeek-AI）与论文动机场景（AI 自我修改）；仓库把 session log、回放、重建做成一等公民——这些恰好是给模型提供训练、评估养料的数据；人类纠错留下的痕迹本质上就是人类反馈数据。但「分团队下注」「招聘导向」属于外部观察，未经内部证实¹⁷。

由此得出的趋势判断：harness 代表的方向是**更短、更快、更及时地在场景中意识到问题，并做领域性改进**。把「发现→打回→重来」的周期从仓库级压缩到插件行级；把改进单位从「改代码库」降到「改组合配置」。这与 RSI 的路线图吻合：模型自改进需要的第一块地基不是更强的模型，而是**搜得动、查得清、退得回的改动机制**。

## 第四问：这么做对么？成立么？长久么？

先给一句话：**事在人为，既然开了这条道，自然会向下走，软件不是静态的。** 但两个隐患姑且写下来，它们一个在生态侧，一个在方法论侧。

### 隐患一：外围产出的动力问题

自我迭代的宣传再响亮，**真正有价值的产出依然在外围**：意图与环境提供者是开发者，场景判断是使用者，语义契约的最终裁决是人。问题是怎么让大家持续产出——不能纯卖流量。

有一个事实锚点：仓库贡献指南（CONTRIBUTING.md）¹⁸原文写着「We are sorry that we cannot accept external pull requests at the moment」——项目 MIT 开源，但**不接受外部代码贡献**；能做的只有 issue 投票、挂 `dsh-plugin` topic 的插件生态、写博客。翻译过来：**开源，但不开放**。参与者没有贡献权、没有名分，产品话语权更谈不上。（推断：根据崔神的招聘列表——包括产品经理岗——看起来更像是把插件生态当养料来健壮自己的产品；招产品经理不做产品就说不过去了。这是外部观察。）

再叠一层历史观察（推断）：DeepSeek 过往的产品除了模型和一些技术框架外，没有开源或共享的传统，更像是「开源但并不开放」的状态。如果生态贡献者既进不了核心仓库、又拿不到产品名分，那么**鱼肥果熟进我肚的可能性非常高**——外围把场景、插件、反馈都喂进来，果实被官方摘走。短期无害（社区拿到的是上手快、有流量的工具），长期会枯竭（持续产出的动力不在）。

### 隐患二：熵减消灭了 agent 自身的可能性

第二层隐患更根本。**当我们为 agent 的自我迭代开始划分节点、领域和规范这些事情的时候，本身就是一种外围策略的熵减——从第一天起就灭绝了 agent 自身的可能性。**

这个代价有一个更精确的表述：**把改动的表达收窄，反而让过拟合变得更便宜**¹⁷。改动怎么表达，和改动怎么评估，是两件分开的事情：划分节点解决的是前者，不解决后者；如果保留标准只是「当前 loop 的成功率」，那么过拟合就不是风险，而是默认结局。也就是说，官方把 harness 组织成什么样子，模型的搜索空间就被剪成了什么样子；而剪这个空间的人，对评估这一侧并没有把握。这也是为什么 DeepSeek 做 RL 的同事只愿意训练 minimal mode 的原因（推断，来自我的外部观察）：那个路线更第一性原理——**最好所有的 harness 都是 agent 自己手搓的**，不要预设结构，把整个设计空间留给模型自己去长。

所以目前的方案有一个错位的满足感：它让周边的开发者很开心（不深入的那种）——有流量、容易上手、口喷即可演化；但真实想搓出 **e2e 的 agent 自我迭代**，还差四样：主动性（谁发起改进）、完整上下文（进程级重启与上下文范畴收敛）、自评估（改动凭什么保留）、以及泛化（历史之外也成立）。这四样没有一样会从「划分节点、领域和规范」里自动长出来。

### 两个隐患的交汇点：生态策略

两个隐患其实在同一个地方交汇：**如果外围参与者只是养料，蠕虫化的只有官方团队**——拟态蠕虫化的潜力会被用来吸收社区机制的精华，而社区拿不到改动权；**如果外围真正拿到改动权与名分，「harness 的爸爸」才可能成立**——因为拟态的能力必须由生态里的多样性供养。开源但不开放，是把这条路走窄的选择。

## 结语

回到四个问题，我的判断是三条：

1. **改动的机制已经就绪。** 插件级回滚、逐字节重建、模糊测试下的稳定，都验证了机制层本身可靠。整个系统只有一种改动方式这件事是真的，不是宣传。这也是 harness 最不该被低估的部分。
2. **胜负手在四样软的东西：主动性、完整上下文、自评估、泛化。** 改动的机制已经就绪，但改进由谁发起、改进时带什么上下文、改完自己怎么评、评完怎么保证历史之外也成立——这四样一样都没有。谁先把这四样做出来，谁就真正拿到自驱动的钥匙。在那之前，harness 是自循环的雏形，不是自驱动的系统。
3. **生态策略是最大变数。** 它决定这是 harness 的爸爸还是又一个养料池。技术门开着，门后的路是组织选择。

关于趋势：更短、更快、更及时的**领域性改进**是可见的未来；真正的**自驱动**不会从这套插件机制里自动长出来，它需要主动性、完整上下文、自评估和泛化这四样先被做出来。在那之前，DeepSeek Harness 的意义是一个让人和 agent 都能用同一种方式改系统的 playground——而 playground 的下一站，取决于这四样什么时候补上。
